# Gap audit and implementation record — 18 November 2026

Audit of the repository against `implementation.md` (the master brief), the gaps that were closed in this pass, how they were verified, and what remains outstanding. "Verified" below means exercised by an automated test or by running the application; anything else is stated as source-level only.

## 1. Environment and baseline findings

| Finding | Effect | Resolution |
|---|---|---|
| No working `node`/`npm` on `PATH`; the docs recorded that dependencies had never been installed and nothing had been run. | No build, test, or migration had ever executed. | Used the local Node 22.18 runtime; dependencies installed with `npm ci`. |
| `prisma generate` hung indefinitely. | Blocked the client and build. | Prisma's update-check request stalls on this network. Set `CHECKPOINT_DISABLE=1` (now also set in the Dockerfile). |
| **The build was broken on `main`.** Seven TypeScript errors in `src/server/paga-payouts.ts` and `app/api/webhooks/paga/accounts/route.ts` from the latest Paga commits. | `next build` fails. | Fixed without changing behaviour: a separate variable for the reimbursement transaction result; JSON-safe audit metadata. |
| Schema drift: a Paga migration creates an index on `WithdrawalRequest.pagaBankDestinationId` that `schema.prisma` does not declare. | The next generated migration would have dropped it. | Declared `@@index([pagaBankDestinationId])` in the schema. |
| **Authorisation bug:** the milestone review form was shown to members with spend authority, but the server action checked project-management rights instead. | A project manager **without** spend authority could approve a milestone, which creates a payment obligation and starts a Paga transfer. A spend approver who was not a manager was silently refused. | `reviewMilestone` now requires `canApproveSpend`, matching the UI and the brief (§5.1). |
| Identity verification requests could never be decided (`decideTrustReview` rejected `IDENTITY` outright), and evidence was URL-only. | No identity verification was possible. | See §2. |
| Every profile save deleted and recreated all portfolio items. | Would cascade-delete any attached files. | Portfolio items are now managed individually; profile saves leave them alone. |
| Lint failed with 43 errors, mostly pre-existing (unescaped apostrophes, `any`). | Lint gate failed. | All errors fixed; 17 pre-existing warnings remain. |
| An uncommitted change to `app/workspace/funding/actions.ts` (Paga USD request outcome handling) predates this pass. | — | Left untouched and not included in this work. Review and commit it separately. |

## 2. Gaps closed in this pass

| Brief section | Gap | Implemented |
|---|---|---|
| §16.5, §26, §35 "portfolio uploads work" | No file uploads anywhere. | `FileAsset` model; private local-disk storage outside the web root (`src/server/storage.ts`) with size, type, extension, and file-signature checks; access-checked downloads at `/api/files/[id]` (`no-store`, `nosniff`, sandboxed CSP); central policy in `src/server/file-access.ts`. Wired into milestone submissions, project messages, task comments, dispute evidence, portfolio items, and trust evidence. |
| §11.1 | Portfolio was one pipe-delimited textarea without description, category, date, skills, or files. | Per-item portfolio manager: title, description, category, month, link and/or file, claimed contribution, skills, public/private toggle, confirmed delete. |
| §12.1 | Identity verification unavailable. | Identity-document upload (PDF or image only, never links). Only platform **Admins** can open or decide identity evidence; Operations sees that it is restricted. Every non-owner access is audit-logged (`IDENTITY_EVIDENCE_ACCESSED`). |
| §12.6 | No appeals or correction requests. | `TrustAppeal`: users appeal rejected trust or assessment decisions, or request corrections. Operations reviews them. Upholding an appeal **reopens** the record for a fresh human decision; it never auto-approves. |
| §16.2–16.4 | No task comments, message replies, or attachments; no notifications on messages. | Task comments, threaded replies, attachments, task cancellation, and notifications to project participants. |
| §17.2–17.3 | No partial settlement; revision requests lacked criterion, revision number, or deadline. | Structured review form (acceptance criterion, requested changes, revised date, "revision n of m"). Buyer-proposed partial settlement (`MilestoneSettlementProposal`) takes effect only when the professional accepts. It creates the obligation for the agreed lower amount and resolves disputes on that milestone. |
| §18.1 | Disputes lacked assigned reviewer, agreement version, evidence, review notes, and the "awaiting evidence" step; parties weren't notified. | Dispute captures the agreement version in force; parties add evidence/statements with files. Operations assigns a reviewer, writes party-visible or internal notes, and must explicitly confirm resolution/closure. Central lifecycle (`src/server/disputes.ts`) prevents reopening closed cases. Parties and staff are notified. |
| §19.1–19.6 | Campaign brief missing objective, audience, geography, schedule, approval/reporting requirements, budget, conversion rules, attribution window, exclusions, and refund treatment. Compensation model implicit. No integration events, refund adjustments, or campaign report. | All brief fields. Explicit fixed / hybrid / commission-only arrangement with validation, written into the creator's contract terms. Signed `/api/webhooks/attribution` for lead, order, refund, and cancellation events: deduplicated, logged with a payload hash, last-click attribution window enforced, live events refused, orders queued for human review. Refunds reverse unpaid bonus obligations or record a Finance adjustment if already paid. Campaign report page with per-creator results and an explicit test/manual-data notice. |
| §20.3 | No common payment adapter interface; no Busha adapter. | `src/server/payment-providers.ts`: one interface for collection, status, payout, refund, webhook, and reconciliation. `MockPaymentAdapter` (always simulated; builds signed test webhooks), `PagaStatusAdapter` (Sandbox status/reconciliation; initiation stays in the audited Paga workflows), and `BushaEvaluationAdapter`, which refuses every operation because no approval exists. |
| §22 | No notification preferences or email adapter for notifications; no task-deadline reminders. | Per-category in-app/email preferences on Settings (account, dispute, and payment updates cannot be muted in-app; email is opt-in). Branded notification email. Simulated payment notifications are labelled "[Simulated]". Protected `/api/jobs/notifications` job sends task-due reminders and delivers emails idempotently. Existing notifications are tagged by category. |
| §23 | No audit-log viewer or webhook monitor. | `/workspace/admin/audit` (filter by action, entity, actor, dates; paginated) and `/workspace/admin/webhooks` (provider adapter status, webhook events, Paga Sandbox callback entries). |

## 3. Verification results

Run on 18 November 2026 against a local Prisma Postgres (`prisma dev`) database:

- `prisma migrate deploy`: all 11 migrations apply to an empty database; `migrate diff` against the schema reports no drift.
- Demo seed: completes; reseeding refreshes accounts without duplicating records.
- `npm run test`: **37 passed, 0 failed** (20 existing + 12 new unit + 5 integration).
- `tsc --noEmit`: clean. `eslint .`: 0 errors, 17 warnings (pre-existing).
- `next build`: **succeeds** (it failed on `main` before this pass).
- `scripts/smoke-e2e.mjs` against the production server: **all checks pass**. Public pages; sign-in through Auth.js for all seven role accounts; each role's pages render with seeded content; cross-role pages (admin, operations, finance, other organisations' projects) are refused.
- Runtime server-action journeys (26 checks, all passing, run once against the production server and not kept in the repo because they depend on build-specific action ids). Covered: a project manager without spend authority cannot approve a milestone; structured revision request; partial settlement accepted only by the assigned professional, creating the obligation and ledger entry for the settled amount; dispute review requires staff role and explicit confirmation to resolve; upheld appeal reopens rather than approves; Operations can neither decide nor download identity evidence while Admin can, with an audit record; deliverable files download for project participants only; notification preferences save.
- The first smoke run surfaced `ConnectionClosed` errors from the single-connection local database under parallel queries. Added optional `DATABASE_POOL_MAX` (set to `1` locally) rather than changing query code.

## 4. Outstanding (not done; needs external input or further work)

- **Malware scanning** of uploads, and an **S3-compatible storage adapter** for multi-instance deployments. Local disk needs a persistent, backed-up volume.
- **Browser end-to-end and accessibility tests** (Playwright or similar, plus WCAG 2.2 AA checks). The smoke test checks server-rendered pages and authorisation, not client interactions.
- **Live campaign attribution**: needs an approved merchant integration; live events are refused.
- **Busha**: evaluation only. Enabling it needs written provider approval, legal review, credentials, and code, not configuration.
- **Paga**: still no end-to-end Sandbox transaction demonstrated; payout failure without a Paga-confirmed reversal and FX differences remain manual. Live is disabled.
- **EUR/GBP payment rails**, production SMTP, error monitoring, backups, a cron caller for `/api/jobs/notifications`, and legal review of the draft Terms and Privacy pages.
- AI scoping and matching were not changed in this pass. Request logging for AI calls and AI-assisted evidence extraction (§12.2) were not reviewed in depth.
